# Project: Aqdi (عقدي)
A Saudi SaaS platform for real-estate offices to manage rental contracts. Six roles on one platform:
platform_admin (me), office_owner (pays), office_manager, office_staff, landlord, tenant.
Offices pay a subscription. Landlords and tenants join free with an invite code.
Contracts are created on the government Ejar platform. This app NEVER connects to Ejar. The office uploads the contract file it downloaded from Ejar, AI reads only dates and amounts, and the app tracks deadlines and sends reminders on four channels.

# Stack (never add a new dependency without asking me first)
Node.js 20 + Express 4 + EJS templates + MySQL (mysql2) + node-cron. No frontend framework, no build step, no ORM.
Exactly these 13 dependencies: express, express-ejs-layouts, ejs, mysql2, dotenv, helmet, cookie-parser, jsonwebtoken, bcryptjs, express-fileupload, nodemailer, node-cron, sharp.
Everything else is written with Node's built-in modules: TOTP with crypto, WhatsApp/Telegram/Moyasar/Claude API with https. Reason: the app runs on shared cPanel hosting where npm install is not re-run on deploy, so a new dependency breaks the deployment.

# Rules you must follow
1. The UI is Arabic, RTL, mobile-first, large text and obvious buttons, for non-technical users. All user-facing text is Arabic; code, comments and commit messages are English.
2. Never add a feature I did not ask for. Simplicity beats cleverness.
3. No Ejar logo, colors or wording that suggests this app is official or governmental. Show where relevant: 'تطبيق خاص غير تابع لمنصة إيجار، والتواريخ للتذكير فقط'.
4. Privacy: never store from a contract the party names, national ID or iqama numbers, IBAN, meter or account numbers, or full addresses. Never log contract contents. Never persist the uploaded contract file.
5. Secrets live only in environment variables or encrypted in the database. .env is gitignored. Never print a secret.
6. Every table that belongs to an office carries office_id, and every query goes through scopeToOffice(). One office must never read another office's row, even through a coding mistake.
7. Dates: store Gregorian (YYYY-MM-DD) and UTC timestamps; display in Asia/Riyadh. Hijri is display-only text. All date math lives in services/contractDates.js (date primitives) and services/contractEngine.js (contract rules), pure functions covered by tests.
8. Money: DECIMAL(12,2) with a separate currency column, SAR by default.
9. Security on the server, never only in the UI: every protected route uses requirePerm. Hiding a button is decoration.
10. After every task: run the tests, fix failures, commit with a clear message, push to main, then tell me in simple Arabic what to check in the browser.

# Office area (routes/office.js, middleware/loadOffice.js)
- Sign-up: /register uses the phone OTP flow. A new phone becomes a user with role NULL; only PLATFORM_ADMIN_PHONE ever becomes platform_admin. Role NULL lands on /office/new, which creates the office in ONE transaction (offices, users.role = office_owner, office_members, office_settings, audit_logs) and is never shown again once the user has a role or any office membership.
- After login: platform_admin -> /platform, office_owner/office_manager/office_staff -> /office, landlord -> /landlord, tenant -> /tenant, no role -> /office/new (services/auth.js homeFor).
- loadOffice runs on every /office route: it takes the office from the signed-in user's ACTIVE office_members row and sets req.office and req.memberRole. Never take an office id from the URL, body or cookie. An inactive member row gets 403. Inside /office, requirePerm checks req.memberRole. The membership lookup by user id (services/offices.js membershipsFor) is the only office-table query not scoped by office, because it is how the office id is found.
- Status rules (services/offices.js officeAccess): trial (not expired) and active = full access; past_due = access plus a red banner; suspended or an expired trial (trial_ends_at in UTC) = every /office page except /office/billing and /office/settings shows "اشتراكك منتهي" (HTTP 402). Trial days left are counted on the Riyadh calendar. A paid period (offices.subscription_ends_at) that ended gives 7 read-only days (readOnly: GET pages work, every other method answers 402 "وضع القراءة فقط" except billing and settings), then locked with reason 'expired'.
- Routes and capabilities: /office (contracts), /office/tenants (tenants), /office/payments (payments.read), /office/maintenance (maintenance), /office/listings (listings), /office/reports (reports), /office/messages (messages), /office/team (team), /office/audit (audit), /office/settings GET (settings.basic) and POST (settings.office), /office/billing (billing). Audit rows never contain the code.

Use inviteGuard.check() in the join route: 5 wrong attempts per IP per 15 minutes, 10 per phone per hour. markInviteUsed(pool, code, userId) is one atomic UPDATE; true for exactly one caller. These two look a code up across offices by design (the person joining has no office yet).

# Date rules (config/ejarRules.js, services/contractEngine.js)
- The Ejar rules exist once, in config/ejarRules.js (frozen). VERIFY every one against the official Ejar/REGA source before launch:
  - NON_RENEWAL_NOTICE_DAYS = 60: notice not to renew is due at least 60 days before end_date.
  - RENT_CHANGE_NOTICE_DAYS = 90: a rent change must be requested at least 90 days before end_date.
  - AUTO_RENEW_DEFAULT = true: without timely notice the contract renews for a term equal to the previous one.
  - RIYADH_RENT_FREEZE = { city: 'riyadh', from: '2025-09-25', years: 5 }: no rent increase in Riyadh when the new rent would take effect (end_date + 1) from 2025-09-25 up to 2030-09-24; a reduction is always allowed.
  - STAGE_THRESHOLDS = { soonDays: 30, urgentDays: 7 }, counted in days left to the notice deadline.
- Stages (classifyContract): terminated > renewed > ended (today after end_date; the end day itself is still running) > deadline_passed (after the notice deadline) > urgent (0..7 days left; the deadline day is urgent) > soon (8..30) > calm (more than 30). A contract that has not started is classified the same way and flagged notStarted.
- "today" is always passed in as riyadhDate(now). Dates are strict 'YYYY-MM-DD' (years 1900-2200; impossible dates throw ContractDateError 'invalid_date'). Months add with clamping to the month end; a term of n months ends on addMonths(start, n) minus one day.
- Money in the engine is integer halalas; schedules put the rounding remainder on the last installment.
- Hijri (formatHijri) is display only, labelled "تقريبي", never used in math.
- Never do date math outside services/contractDates.js and services/contractEngine.js, and never write a rule number anywhere but config/ejarRules.js.

# Contracts (routes/contracts.js, services/contracts.js, services/contractStatus.js)
- Routes (all 'contracts' unless noted): GET /office/contracts (filters stage incl. 'action', landlord, ends=30|60|90|180, q; sort deadline|end|created; 20 per page), GET /office/contracts/new, POST /office/contracts/preview (JSON, real engine, no database, 60 per minute per user), POST /office/contracts, GET /office/contracts/:id, GET+POST /office/contracts/:id/edit, POST /office/contracts/:id/payments/:paymentId ('payments.write'), GET+POST /office/contracts/:id/terminate ('contracts.terminate': owner and manager), GET+POST /office/contracts/:id/renew, POST /office/contracts/:id/delete ('contracts.delete'), POST /office/contracts/:id/invite (max 20 per office per hour), POST /office/contracts/:id/invite/revoke.
- Capabilities added for this: 'contracts.terminate' (owner, manager) and 'payments.write' for office_staff.
- The save logic (services/contracts.js) does not care where the numbers came from (hand entry now, AI later): it re-validates with the engine, never trusts the preview. Sanity errors block; warnings need the "راجعت التنبيهات" tick.
- Create = ONE transaction: contract plan limit (planLimits.contractUsage first; counts calm/soon/urgent/deadline_passed), unit row lock, unit must be vacant and of the same landlord, no overlap with another non-terminated contract on the unit (back to back is fine), contract with engine deadlines and stage, schedule rows, unit status, tenant invite, contract_events and audit row. Events and audit never hold the rent, the tenant label, the termination reason or notes.
- Unit becomes rented when the contract has started or starts within engine APP.rentedLeadDays (30). Otherwise the unit stays vacant with a 'unit_rent_pending' event, and recomputeStatuses flips it later.
- Immutable after save: dates, rent, frequency, unit and landlord. Only tenant_label, contract_number, deposit, commission and auto_renew are editable. To change the rest: terminate and create a new contract.
- Renewal creates a NEW contract for engine nextTerm() (renewed_from_id), marks the old one 'renewed' (renewed_at, renewed_to_id), keeps the unit rented, creates no new tenant invite, and refuses a rent increase while rentChangePolicy() says the Riyadh freeze applies. Terminated or renewed contracts cannot be renewed. Deleting a renewal restores the contract it renewed.
- Terminate: status 'terminated', terminated_at, reason; revokes tenant invites; waives future 'due' payments ("تم الإنهاء"); frees the unit unless another running contract occupies it.
- Delete: only without paid payments (checked in the DELETE) and never for ended or renewed contracts.
- Payments: due / paid / late / waived. Paid needs a date not in the future; receipt numbers are Latin letters and digits only (no names). A 'due' payment past its date shows as late (engine paymentDisplayStatus) and is stored as late by the recompute.
- services/contractStatus.js: planStatusChanges (pure) and recomputeStatuses({ pool, today, officeId? }) update stale stages in batches of 500, repair stored deadline copies from the engine, free units of ended contracts, rent units of started contracts and mark overdue payments late. Idempotent, retried on deadlock. No cron yet: the office home and contracts list call maybeRecompute, at most once an hour per office (office_settings 'contracts.status_recomputed_at'); a failure there is logged and the page still loads.
- Screens compute deadlines from end_date with the engine; the stored notice_deadline / rent_change_deadline copies are only for sorting and filtering.
- Hijri dates on contract screens are labelled "تقريبي".

The server whitelists those keys, drops any value shaped like a national ID (10 digits starting 1 or 2) or an IBAN (SA + 22 digits), validates every value with the engine, and computes deadlines and stage itself. A read reserves a slot first (office row locked, so parallel reads cannot pass the limit) and releases it if the read fails, so only successful reads count; over the limit there is no API call. Plus 5 requests per office per minute (in memory).

# Reminders, notifications and cron (services/reminders.js, notifications.js, delivery.js, channels/*, channelSettings.js, contacts.js, cron.js)
- computeDueReminders({ pool, today, lastRun, now }): for every office with access (officeAccess not locked), every contract not terminated/renewed, it asks the engine (thresholdOn, reminderDays) which thresholds of the office's reminder_rules fall exactly on the day. Kinds: decision_60 (days before engine noticeDeadline, default 60,45,30,14,7,3,1), rent_change_90 (before rentChangeDeadline, 90,60,30), payment_due (before due_date, 7,3,0), payment_late (after due_date, 1,3,7), contract_ended (after end_date, 1). Live stages only, except contract_ended; only 'due'/'late' installments.
- Audience: the office member who created the contract (if still an active member, else the owner), the joined landlord, the joined tenants (payments: office and tenant only).
- Idempotent: notifications.dedupe_key = kind:c<contract>[p<payment>]:<audience>-<user>:<n>:<day> (UNIQUE, INSERT IGNORE). Catch-up: days after settings 'reminders.last_run_date', at most engine APP.reminderCatchUpDays (3) back, title prefixed "متأخر: "; a first run has no catch-up.
- Text: nicknames (unit label, office name), dates (wrapped LTR) and amounts only, always ending with the disclaimer (notifications.withDisclaimer). When rentChangePolicy says no increase (Riyadh freeze): office/landlord get only the freeze notice, the tenant only the reduction reminder; never rent-increase wording.
- Channels: site = the notification row (always on). email / whatsapp / telegram = delivery_log rows (pending/sent/failed/skipped, error_code only; never text, address or secret), queued per notification_prefs (rows (user, channel, 'all'); the ('site','all') row holds quiet_start/quiet_end, default 21:00-08:00 Riyadh). Non-urgent messages wait for the end of quiet hours (contractDates.afterQuietHours); urgent = a 'before' threshold of 0 or 1 day.
- deliverPending claims each row with an UPDATE, sends, retries a retryable failure after 1 min, 10 min, 1 hour, then marks it failed. Missing SMTP, no verified contact, channel not set up or switched off = skipped. One channel never blocks another.
- Drivers: email via nodemailer (SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASS, MAIL_FROM); WhatsApp via a provider interface (Meta Cloud API, template messages only); Telegram Bot API sendMessage (plain text). All HTTPS goes through services/channels/transport.js (10 s timeout); under NODE_ENV=test or the node test runner nothing real is called unless a mock is set.
- channel_settings: per office, credentials sealed with SECRET_BOX_KEY, never logged or sent back (page shows "مضبوط ✓"; blank field keeps the stored value). Saving Telegram calls getMe and setWebhook to /webhooks/telegram/<random secret>; only the sha256 of the secret is stored and compared in constant time; unknown secret = 404. user_contacts: WhatsApp = login phone or another number confirmed by SMS code; Telegram = one-time 8-character code (15 min, hashed) sent to an office bot.
- Notifications are read and changed only by their user_id (another id = 404). Bell count in both layouts (middleware loadUnreadCount). /office/settings/reminders needs 'settings.office'.
- cron.js: node-cron, Asia/Riyadh, started by server.js unless RUN_CRON=false. Jobs: reminders 07:00, deliver */5, recompute 00:10, late_payments 00:20, digest 08:00, expire_invites hourly (unused codes expired 30+ days), trial_check 09:30, purge_notifications Fri 03:00 (notifications 180 days, delivery_log 90 days), purge_auth */10; plan_renewal 06:00 (subscriptions, see Billing); placeholders backup, sms_balance, health_ping, reports are registered but off. Each run holds GET_LOCK('aqdi:job:<name>') and is recorded in cron_runs. POST /cron/run/:job with X-Cron-Secret (constant-time) answers only { ok, processed }.

# Billing, plans and the platform admin (config/billing.js, services/pricing.js, plans.js, subscriptions.js, subscriptionState.js, promos.js, orders.js, moyasar.js, bankTransfers.js, invoices.js, platformSettings.js, features.js, admin.js; routes/billing.js, routes/admin.js)

No floats. Orders and invoices store DECIMAL(12,2) plus currency 'SAR'.

- services/subscriptionState.js (pure, fixed clock in tests): periodState active | grace (7 days) | expired, planTransition (active -> past_due after the end, -> suspended after the grace), reminderThreshold 7/3/1. subscriptions.runDaily (cron plan_renewal, optional officeId) moves statuses, notifies the owner (kinds sub_reminder, sub_expired, sub_suspended; dedupe keys sub_remind:o<id>:<end day>:<n>, sub_expired:..., sub_suspended:...) and expires unpaid orders (24 h card, 72 h transfer without a sent reference), freeing promo reservations. Suspended data is kept 90 days as a policy; nothing is deleted automatically.
- Orders (pending | paid | failed | expired, suspicious flag): createOrder is ONE transaction: office row locked first, plan and downgrade check, earlier unpaid orders of the office expired, promo locked and checked, order and a 'reserved' promo_usages row. settle / settleInTx is the only place an order becomes paid: locks the order, UNIQUE (provider, provider_ref) in platform_payments makes it idempotent (replay = no-op), amount or currency mismatch = suspicious (nothing activated, platform admin notified, kind billing_alert), a second payment for a paid order = flagged, a late matching payment for a failed or expired order is accepted. A zero total (100% promo) is settled without a payment (provider 'manual').
- Moyasar (services/moyasar.js, built-in https, TEST MODE ONLY): MOYASAR_SECRET_KEY, MOYASAR_PUBLISHABLE_KEY, MOYASAR_WEBHOOK_SECRET from the environment only; live keys refused unless MOYASAR_ALLOW_LIVE=1; missing keys = "الدفع الإلكتروني غير مفعّل" and bank transfer still works. The redirect callback and POST /webhooks/moyasar only supply a payment id; fetchPayment(id) calls GET /v1/payments/:id and settleMoyasar compares status, amount (halalas), currency and metadata.order_id with the order. Webhook: secret_token must be a string and match in constant time, otherwise 404 (also when no webhook secret is configured). We store only payment id, status, amount, last 4 digits; never card data, names or the raw payload. The hosted-form page has its own CSP (routes/billing.js moyasarCsp). The API shapes are from public docs: verify once in test mode before launch.
- Promo codes: percent (basis points) or fixed, valid from/to (Riyadh days; valid_to stored exclusive), max redemptions, plan_ids, once per office (UNIQUE promo_id + office_id). Reserved under promos.lockAndCheck (row lock + locking read), redeemed when the order is paid, released when it fails, expires or a transfer is rejected.
- Bank transfer: reference up to 40 characters (paymentEntries.validateReference: no IBAN-like or 10+ digit strings), optional receipt image re-encoded by sharp (images.processImage) into UPLOAD_DIR, served only to the owning office (billing capability) and the platform admin. bankTransfers.approve settles in the same transaction (settleInTx); reject needs a reason, fails the order and frees the promo. Both sides are notified (billing_paid, billing_transfer, billing_alert).
- Invoices (subscription_invoices, invoice_counters): INV-YYYY-000001 (Riyadh year), gap-free through the counter row locked inside the issuing transaction; credit notes CN-... with their own sequence, negative amounts, one per invoice (the original becomes 'credited', its payment 'refunded'; the money is returned outside the app). Snapshot of seller (platformSettings.seller at that moment), buyer = office display name only, lines, discount, VAT, total. Title is "فاتورة ضريبية مبسطة" only when the seller VAT number is set, otherwise "إيصال دفع"; credit notes "إشعار دائن" / "إشعار استرداد". No ZATCA claim anywhere; ZATCA Phase 2 is a separate later task. The seller details are empty-safe platform settings (settings table keys seller.*, bank.*, support_phone, support_email); never hardcode a company or VAT number.
- Office billing (capability 'billing' = owner only): GET /office/billing, GET /office/billing/checkout, POST /office/billing/orders, GET /office/billing/orders/:id/pay, GET /office/billing/moyasar/callback, GET+POST /office/billing/orders/:id/transfer, GET /office/billing/receipts/:id, GET /office/billing/invoices/:id (printable A4, ownership by office id, 404 otherwise). These stay open when the office is locked or read-only.
- Platform admin (routes/admin.js, services/admin.js; capability 'platform.access'): /admin guard = noStore, sameOrigin, requireAuth, requirePerm, a 2FA check (a platform_admin session whose user has no 2FA is refused while 2FA is required), layouts/admin. Pages: / (cards: offices by status, MRR from active subscriptions, new offices this Riyadh month, contracts, notifications and deliveries in 7 days, AI reads), /offices (+ /:id with extend-trial, plan, suspend, unsuspend, note), /orders (+ /invoices/:id, credit-note), /transfers (+ approve, reject, receipt), /promos, /plans, /settings (details and kill switches), /audit (filters: action prefix, office, actor phone, dates). Every state-changing POST needs a written reason (3 to 200 characters) and writes an audit row (actions admin.*, billing.transfer_*) with that reason in after_json; values of settings are never in the audit row, only the changed key names. No party data on any admin page and no impersonation. /platform redirects to /admin (homeFor still answers '/platform').
- Kill switches (settings keys kill.signups_disabled, kill.ai_disabled, banner.message): signups off blocks NEW phones in findOrCreateUser (SignupsDisabledError; the admin phone and existing users are never blocked) and POST /office/new; AI off answers before any API call (features.aiAvailability); the banner is held in memory (platformSettings.bannerNow, refreshed by server.js every 30 s, never read from the database inside a request). Tests never flip the signup or AI switches in the shared database (injected settings instead).
